# macOS auto-update from GitHub releases

Researched 2026-09-10. Sources are the Zed, Sparkle, Tauri, cargo-packager and self_update source trees at pinned commits, Apple's documentation and Quinn's DTS forum posts, and GitHub's REST and release documentation.

## Decision for Cadence

Embed Sparkle 2 and let it update from the DMG the release workflow already produces. Publish a signed `appcast.xml` as one more release asset and point `SUFeedURL` at GitHub's permanent latest-asset URL. Drive Sparkle from Rust with a handful of `msg_send!` calls, which the GPUI app Waku already does in production. Waku hosts its own appcast on Cloudflare R2, but nothing in Sparkle requires that, and GitHub's permanent latest-asset URL removes the need for a second host.

Sparkle owns the parts that are hard to get right in a first implementation: rejecting a download unless its EdDSA signature or its Developer ID signature matches the running app, releasing quarantine, swapping the bundle atomically, asking for administrator rights only when the bundle is not writable, and relaunching. The price is one new secret, a framework inside the bundle with three extra `codesign` calls, and an appcast step in CI.

The alternative that fits the codebase if the ObjC surface is unwelcome is a small Rust updater on the GitHub REST API that verifies the mounted app with Apple's own code signature APIs and swaps the bundle by rename. Zed and Zeron ship that shape. Neither Zed nor the Rust updater crates verify the Apple signature of what they install, so that check would have to be written here. The detailed tradeoffs are in the recommendation section.

The GPUI restart primitive Cadence already links spawns `bash` that waits for the current pid to exit and then runs `open` on the bundle, then quits the app. `app_path` is `NSBundle.mainBundle.bundlePath`. [gpui-pre-macos 0.3.4 `restart`](https://docs.rs/crate/gpui-pre-macos/0.3.4/source/src/platform.rs#543-583) [gpui-pre-macos 0.3.4 `app_path`](https://docs.rs/crate/gpui-pre-macos/0.3.4/source/src/platform.rs#1037-1042) [gpui-pre 0.3.4 `restart` and `set_restart_path`](https://docs.rs/crate/gpui-pre/0.3.4/source/src/app.rs#1619-1631)

Two properties of Zed's design matter for Cadence. The `rsync --delete` into the live bundle replaces files one at a time, so a crash mid-copy leaves a bundle with a broken signature, and the code relies on the downloaded DMG never carrying a quarantine attribute, which is true because Zed's own HTTP client writes the file and the app does not opt into quarantine (see Apple constraints).

Release assets have permanent per-tag URLs of the form `https://github.com/OWNER/REPO/releases/download/TAG/ASSET`, and `https://github.com/OWNER/REPO/releases/latest/download/ASSET` resolves to the same asset name on the newest non-prerelease, non-draft release. [Linking to releases](https://docs.github.com/en/repositories/releasing-projects-on-github/linking-to-releases) [Get the latest release](https://docs.github.com/en/rest/releases/releases?apiVersion=2022-11-28#get-the-latest-release)

### Trust model

Sparkle validates the downloaded archive with the EdDSA key first. If that fails and the archive is Developer ID signed by the same Team ID as the running app, it accepts the download as a key rotation path. After extraction, an app bundle must pass Apple code signature validation against the old app's designated requirement, or the EdDSA check, and an update that is code signed but invalidly so is rejected. Removing a public key or removing code signing from one version to the next is refused as policy. [`SUUpdateValidator.m` L60-L91](https://github.com/sparkle-project/Sparkle/blob/5f2b248e3e69e45a5cff42ff7594f168225ebaa5/Sparkle/SUUpdateValidator.m#L60-L91) [L271-L281](https://github.com/sparkle-project/Sparkle/blob/5f2b248e3e69e45a5cff42ff7594f168225ebaa5/Sparkle/SUUpdateValidator.m#L271-L281) [L333-L372](https://github.com/sparkle-project/Sparkle/blob/5f2b248e3e69e45a5cff42ff7594f168225ebaa5/Sparkle/SUUpdateValidator.m#L333-L372) [`SUCodeSigningVerifier.m` L26-L77](https://github.com/sparkle-project/Sparkle/blob/5f2b248e3e69e45a5cff42ff7594f168225ebaa5/Autoupdate/SUCodeSigningVerifier.m#L26-L77) [Developer ID team requirement L323-L363](https://github.com/sparkle-project/Sparkle/blob/5f2b248e3e69e45a5cff42ff7594f168225ebaa5/Autoupdate/SUCodeSigningVerifier.m#L323-L363)

Apple code signing alone is not enough to skip the EdDSA key. The migration guide only allows dropping the legacy DSA key when updates are Developer ID signed with the same certificate. [EdDSA migration](https://sparkle-project.org/documentation/eddsa-migration/)

The framework must be embedded and signed with the app's identity. With hardened runtime and library validation, the framework needs the same identity as the app or `dlopen` rejects it. ## Recommendation

### Option A, Sparkle from the existing DMG (recommended)

Runtime changes:

1. `package-app.sh` downloads the pinned Sparkle tarball once (URL and SHA-256 checked in, cached outside `target/`), copies `Sparkle.framework` into `Contents/Frameworks`, deletes `XPCServices`, `Headers`, `PrivateHeaders` and `Modules` because Cadence is not sandboxed, and signs `Versions/B/Autoupdate`, `Versions/B/Updater.app` and the framework with the same `sign` function before signing the app. Waku's script is the template. [`bundle.sh` L130-L200](https://github.com/egoist/waku/blob/b68baeddebfa0b67878c863de2f23619310a460a/scripts/bundle.sh#L130-L200)
2. `Info.plist` gains `SUFeedURL` `https://github.com/infomiho/cadence/releases/latest/download/appcast.xml`, `SUPublicEDKey`, and `SUEnableAutomaticChecks` YES. Keep the default one day interval.
3. A `src/updater.rs` module, macOS only, `dlopen`s the framework at startup, allocates `SPUStandardUpdaterController` with `initWithStartingUpdater:YES updaterDelegate:nil userDriverDelegate:nil`, keeps it alive for the process, and exposes `checkForUpdates:` for a "Check for Updates" menu item. Skip Sparkle entirely for debug builds and ad-hoc signed bundles, as Waku does, so a development build never offers to replace itself with a release. [Programmatic setup](https://sparkle-project.org/documentation/programmatic-setup/) [`updater.rs` L590-L593](https://github.com/egoist/waku/blob/b68baeddebfa0b67878c863de2f23619310a460a/src/updater.rs#L590-L593)

Release workflow changes:

1. One-time: run `generate_keys` locally, back up the private key, put the public key in `Info.plist`, and store the exported private key as a `SPARKLE_PRIVATE_KEY` secret through `setup-release-signing.sh`.
2. After notarization, run `generate_appcast --ed-key-file - --download-url-prefix "https://github.com/infomiho/cadence/releases/download/$GITHUB_REF_NAME/" -o dist/appcast.xml dist/` with the secret on stdin, and fail the job if any enclosure lacks `sparkle:edSignature`. Waku checks that because `generate_appcast` exits 0 after writing an unsigned feed when the key does not match. [`appcast.ts` L64-L100](https://github.com/egoist/waku/blob/b68baeddebfa0b67878c863de2f23619310a460a/scripts/appcast.ts#L64-L100)
3. `gh release create ... dist/*` already uploads everything in `dist/`, so `appcast.xml` becomes a release asset with no extra step. The tag release notes could be written to `dist/Cadence-<version>.md` first so the appcast carries a `releaseNotesLink`.

Tradeoffs:

- Gains: EdDSA plus Apple signature validation of every download, quarantine release, atomic swap, admin prompt only when needed, translocation and read-only detection, delta updates later if the CI job pulls older DMGs into the directory, Sparkle's own progress and release-notes windows.
- Costs: 2.4 MB of framework in the bundle after the trim above (3.0 MB untrimmed, measured on Sparkle 2.9.6), one more secret and key to never lose, three extra signing invocations, the prebuilt universal `generate_appcast` from the same tarball running in CI, and ObjC message sends from Rust.
- Constraints: `CFBundleVersion` must stay comparable and increasing. Cadence writes the semver string there, which works for dotted numeric releases but not for pre-release suffixes, so either forbid pre-release tags or derive a numeric build number as Waku does. [`RELEASING.md` L110-L115](https://github.com/egoist/waku/blob/b68baeddebfa0b67878c863de2f23619310a460a/RELEASING.md#L110-L115) [Documentation](https://sparkle-project.org/documentation/)
- A single-item appcast per release is enough for Sparkle because it only needs the newest item that satisfies `minimumSystemVersion`. Older users who skipped several versions jump straight to the latest.

### Option B, Rust updater on the GitHub REST API

Shape: hourly `GET /repos/infomiho/cadence/releases/latest`, pick the `Cadence-*-macOS-arm64.dmg` asset, download to a temp dir through the existing `reqwest` fork, hash it against the asset `digest`, `hdiutil attach -nobrowse`, verify the mounted bundle with `SecStaticCodeCheckValidity` against the running app's designated requirement (or shell out to `codesign --verify --strict -R=<requirement>`), `ditto` it beside the installed bundle, rename old aside, rename new in, `hdiutil detach`, and call `cx.set_restart_path` and `cx.restart()`. Refuse to update when the bundle path contains `AppTranslocation` or the parent directory is not writable, and show a "download the new version" link instead. Zeron's `apply_mac_app` and `relaunch_app_after_exit` are the closest existing code for the swap and relaunch, with the Team ID check added before the swap. [`apply_mac_app` L408-L435](https://github.com/zeronsh/comet/blob/2701c17c013dd09ee3095bad56c946b2276eff11/crates/update/src/lib.rs#L408-L435)

Tradeoffs:

- Gains: no framework, no new secret, no ObjC beyond what `objc` 0.2 already offers, the same artifact as today, and full control of the UI.
- Costs: the swap, verification, cleanup on failure, and authorization fallback are Cadence's to write and test. Zed skips verification entirely, and the two Rust crates that do the swap first `rm -rf` the installed bundle. `self_update` 1.3.0 is the closest ready-made piece, but it wants a tar.gz or zip rather than the DMG and brings a second HTTP stack.
- Trust root is only the Apple signature and TLS to GitHub. That is what Sparkle itself falls back to, so it is defensible, but a compromised GitHub account could ship a bundle signed by nobody unless the Team ID requirement is enforced, so the requirement check is not optional.

### Not recommended

- `cargo-packager-updater`: last release July 2025, non-atomic install, minisign key management with no Apple signature check, and a second artifact.
- `tauri-plugin-updater`: coupled to the Tauri runtime.
- Zed's `rsync --delete` into the live bundle: violates the rename-only rule for signed code between the first and last file, and leaves a broken bundle if interrupted.

## Validation before shipping

1. Install a signed build under `/Applications` as an admin user, launch, and confirm the appcast URL resolves through GitHub's 302 to the versioned asset and that Sparkle's log shows the EdDSA signature accepted.
2. Repeat with the bundle owned by another account to see the "wants permission to update" prompt.
3. Launch the DMG's app directly from `~/Downloads` without moving it and confirm the updater reports nothing rather than failing.
4. Run `ls -i /Applications/Cadence.app/Contents/MacOS/Cadence` before and after an update and confirm the inode changed.
5. Confirm `codesign --verify --deep --strict` and `spctl --assess --type execute` pass on the updated bundle, and that Keychain access still works without prompts, since the designated requirement must be unchanged across versions (see [keychain-ux](keychain-ux.md)).
