# HN 49520837: librespot risk and Spotify Soloist

Research date: 2026-09-01. Fastpotify source claims were checked against repository commit [`d17b2f0`](https://github.com/crmne/fastpotify/tree/d17b2f0611299d74bcda840ac10be98be1044e62).

## Decision for Cadence

Do not switch Cadence from librespot to Spotify Soloist today. Spotify has not deprecated librespot; librespot is an independent, unsupported project that Spotify never supported in the first place. There is nevertheless a material continuity risk: Spotify has restricted some unofficial playback authentication paths, and an unresolved account-dependent audio-key failure prevents playback for some users. Soloist is evidence that Spotify now offers an official alternative for headless Linux receivers, but it cannot currently replace an embedded macOS playback library.

## Identification

The supplied HN item is not a submission: it is a [comment](https://news.ycombinator.com/item?id=49520837) in the [Fastpotify submission](https://news.ycombinator.com/item?id=49517448). The submitted project is **Fastpotify**, an independent, MIT-licensed Spotify desktop client for Linux, macOS, and Windows, written in Rust with egui and using librespot for playback. It is not Spotify's client, a web wrapper, or a server; the project explicitly excludes a browser engine, telemetry, and a hosted backend. [Fastpotify overview](https://github.com/crmne/fastpotify/blob/d17b2f0611299d74bcda840ac10be98be1044e62/docs/_guide/what-is-fastpotify.md) [Project boundaries](https://github.com/crmne/fastpotify/blob/d17b2f0611299d74bcda840ac10be98be1044e62/AGENTS.md#product-boundaries)

The comment introduces **Spotify Soloist** as an “official alternative to librespot.” Soloist is a separate official Spotify product: a headless Linux command-line client for Raspberry Pi and similar devices, with local audio, Spotify Connect, optional local WebSocket control, and no local UI. Thus it overlaps with Fastpotify's local playback/Connect layer, not with Fastpotify as a complete desktop client. Spotify documents Soloist as an executable process, not as a drop-in Rust library replacement for librespot. [Soloist overview](https://developer.spotify.com/documentation/soloist/concepts/overview) [Soloist features](https://developer.spotify.com/documentation/soloist/features)

The parent HN comment makes the stronger claim that Spotify is “in the process of killing the librespot project.” Its follow-up evidence is that librespot no longer works for new accounts, APIs are being gated, and Spotify is applying legal pressure. The first two points have some supporting evidence, although “all new accounts” is not established; the legal-pressure assertion is uncited. Fastpotify's author replies that they have seen no evidence of Spotify killing librespot and suspects conflation with Web API restrictions. [Parent claim](https://news.ycombinator.com/item?id=49517870) [Claim follow-up](https://news.ycombinator.com/item?id=49518819) [Fastpotify author reply](https://news.ycombinator.com/item?id=49519936)

## Is librespot being deprecated?

No official source reviewed says that librespot is deprecated or has a scheduled shutdown. Spotify's Soloist announcement and documentation do not mention librespot. A sentence in librespot's README saying it is an alternative to the “official and now deprecated” library refers to Spotify's old closed-source **libspotify**, not **librespot**. [Soloist announcement](https://developer.spotify.com/blog/2026-08-13-introducing-spotify-soloist) [librespot README](https://github.com/librespot-org/librespot#librespot)

“Deprecated” is also the wrong lifecycle term because Spotify does not own or support librespot. Librespot reverse-engineers private Spotify playback behavior, and its maintainers warn that using it is probably forbidden by Spotify and is at the user's own risk. Spotify can change those private interfaces without deprecating them first. [librespot disclaimer](https://github.com/librespot-org/librespot#disclaimer)

The technical risk behind the HN claim is real:

- In November 2025, librespot issue [#1649](https://github.com/librespot-org/librespot/issues/1649) documented successful OAuth and session authentication followed by `audio key error 0 1`, which prevents decryption and playback. A maintainer inferred that Spotify “may be phasing out this way of getting the key,” but Spotify has not confirmed that interpretation. Later reports indicate account-dependent behavior, including failures that follow the account across devices and implementations.
- In August 2026, issue [#1737](https://github.com/librespot-org/librespot/issues/1737) documented externally supplied third-party access tokens being rejected for private playback operations. The current workaround is to establish a session and persist reusable credentials using Spotify's desktop client identity. Librespot merged an example for that route in [#1744](https://github.com/librespot-org/librespot/pull/1744) and a device-authorization option in [#1745](https://github.com/librespot-org/librespot/pull/1745), so the project remains actively maintained.
- Spotify's 2025 and 2026 Web API restrictions are separate from audio playback. They reduce what new Development Mode applications can browse or modify, but do not themselves deprecate librespot. [Extended-access criteria](https://developer.spotify.com/blog/2025-04-15-updating-the-criteria-for-web-api-extended-access) [February 2026 migration guide](https://developer.spotify.com/documentation/web-api/tutorials/february-2026-migration-guide)

Cadence already uses the August workaround: the Spotify desktop client ID, its expected loopback redirect, PKCE, and then reusable playback credentials. [Cadence playback authorization](../../src/playback.rs) Therefore the `INVALID_CREDENTIALS` break described in #1737 should not require a Cadence migration. The unresolved #1649 audio-key failure is the serious exposure: affected users may authenticate successfully and still be unable to play anything, and neither a different OAuth redirect nor Soloist's device authorization flow fixes that protocol/account restriction.

## Can Cadence switch to Soloist?

Not with Spotify's current product:

| Requirement | Soloist today | Consequence for Cadence |
| --- | --- | --- |
| macOS runtime | Downloads exist only for Linux ARM32, ARM64, and x86_64 | It cannot run on Cadence's supported platform |
| Embedding | Distributed as a standalone `soloist` executable with CLI and local WebSocket control; no library or SDK is documented | It cannot replace the in-process Rust `Session`, `Player`, and event channel |
| Audio integration | Outputs through Linux PipeWire or PulseAudio | It cannot feed Cadence's custom CPAL/CoreAudio sink |
| Distribution | Spotify says not to redistribute Soloist archives or binaries | Cadence cannot bundle it in the app |
| Updates | Builds expire 90 days after their build date and then exit | It is incompatible with normal self-contained desktop releases without a Spotify-supported updater |
| Authentication | Every user must generate a secret Soloist API key, which must not be embedded in client applications, then pair through Spotify Connect | Cadence's current onboarding and Keychain model would need a second, more burdensome secret flow |
| Control parity | WebSocket supports common controls, events, metadata, and queue observation, but not the full direct-player/custom-output interface Cadence uses | A process adapter would still lose capabilities and would not solve the platform or distribution blockers |

Sources: [Soloist overview](https://developer.spotify.com/documentation/soloist), [downloads and redistribution](https://developer.spotify.com/documentation/soloist/reference/downloads-and-updates), [authentication](https://developer.spotify.com/documentation/soloist/concepts/authentication), [WebSocket API](https://developer.spotify.com/documentation/soloist/reference/websocket-api).

The migration should be reconsidered only if Spotify provides a macOS build or embeddable SDK, permits redistribution, exposes custom PCM output or CoreAudio, replaces expiring binaries with a supported update model, and offers an application-safe authentication flow. An explicit Spotify shutdown of the private playback path, or sustained unresolved failures across existing Cadence accounts, would also force a new decision.

## Architecture

Fastpotify is one native application with two Spotify-facing planes:

1. **Browsing and control:** a custom `reqwest`-based Spotify Web API client supplies account, catalog, library, playlist, queue, and remote-device operations. An `ApiGateway` owns separate shared-app and optional personal-app sessions, verifies that they belong to the same account, and routes operations according to API coverage and playlist ownership. [Connection model](https://github.com/crmne/fastpotify/blob/d17b2f0611299d74bcda840ac10be98be1044e62/docs/_reference/how-it-connects.md#independent-grants-once-each) [Gateway source](https://github.com/crmne/fastpotify/blob/d17b2f0611299d74bcda840ac10be98be1044e62/src/api/gateway.rs)
2. **Local playback and Connect:** embedded librespot owns one Spotify session, player, mixer, and Spirc Connect state machine. Player events are folded into a `LocalState` snapshot; commands go to Spirc so Spotify's distributed Connect state stays synchronized. Librespot itself is an open-source Spotify client library that can play through multiple backends and act as a Connect receiver. [Player source](https://github.com/crmne/fastpotify/blob/d17b2f0611299d74bcda840ac10be98be1044e62/src/player.rs#L1-L8) [librespot project](https://github.com/librespot-org/librespot)

Web API authorization uses OAuth Authorization Code with PKCE, appropriate for a desktop client that cannot safely keep a client secret. Local playback has a separate librespot authorization and reusable credential; it is not the same grant as either Web API session. [Fastpotify connection model](https://github.com/crmne/fastpotify/blob/d17b2f0611299d74bcda840ac10be98be1044e62/docs/_reference/how-it-connects.md#independent-grants-once-each) [Spotify PKCE specification](https://developer.spotify.com/documentation/web-api/tutorials/code-pkce-flow)

The application model is an in-memory state tree: pages use explicit `NotLoaded`/`Loading`/`Loaded`/`Failed` states and paged collections, while `App` holds library data, entity-page maps, track caches, navigation, queue state, pending requests, and optimistic overlays. Views emit `Action` values; `App` applies them after drawing. User actions are intentionally shown immediately, with stale Spotify responses prevented from reverting the optimistic state. [Model source](https://github.com/crmne/fastpotify/blob/d17b2f0611299d74bcda840ac10be98be1044e62/src/model.rs) [Application state](https://github.com/crmne/fastpotify/blob/d17b2f0611299d74bcda840ac10be98be1044e62/src/app.rs#L135-L360) [Architecture rules](https://github.com/crmne/fastpotify/blob/d17b2f0611299d74bcda840ac10be98be1044e62/AGENTS.md#architecture)

## Runtime model

- egui/eframe runs the immediate-mode UI on the main thread. It is event-driven: background events call `request_repaint`, allowing the interface to idle when nothing changes. [Backend design](https://github.com/crmne/fastpotify/blob/d17b2f0611299d74bcda840ac10be98be1044e62/src/backend.rs#L1-L7) [egui runtime model](https://github.com/emilk/egui#why-immediate-mode)
- A dedicated `fastpotify-backend` OS thread owns a two-worker Tokio runtime. It hosts librespot, Web API work, sign-in, and artwork fetching. UI-to-backend commands use Tokio MPSC; backend-to-UI events use a nonblocking standard channel. [Backend implementation](https://github.com/crmne/fastpotify/blob/d17b2f0611299d74bcda840ac10be98be1044e62/src/backend.rs#L574-L683)
- The application, audio engine, tray, and media controls outlive the window. Closing to the tray destroys the eframe window; the main loop can create another around the retained `App`. A second launch contacts the existing process instead of creating another application instance. [Main lifecycle](https://github.com/crmne/fastpotify/blob/d17b2f0611299d74bcda840ac10be98be1044e62/src/main.rs#L310-L405)
- MilkDrop is the deliberate process boundary. The same executable is launched in a child mode with its own winit event loop and OpenGL context; post-EQ, pre-volume audio crosses through a shared-memory ring because eframe already owns the main process's event loop. [MilkDrop source](https://github.com/crmne/fastpotify/blob/d17b2f0611299d74bcda840ac10be98be1044e62/src/milkdrop.rs#L1-L27)

## Storage and data model

Persistence is file-based rather than a general local database. The documented model separates configuration, durable state, and disposable caches:

- A readable, atomically replaced `settings.json` stores preferences. `session.json` stores restorable UI/playback state such as navigation, queue rows, sorts, window geometry, and the last track/position. Local play history is another bounded JSON list. [Settings source](https://github.com/crmne/fastpotify/blob/d17b2f0611299d74bcda840ac10be98be1044e62/src/settings.rs) [History source](https://github.com/crmne/fastpotify/blob/d17b2f0611299d74bcda840ac10be98be1044e62/src/history.rs#L1-L18)
- Shared and personal Web API refresh tokens and the separate librespot credential live in the platform state directory. Audio, artwork, lyrics, and account-scoped playlist snapshots live under the cache directory. Cached playlists contain a Spotify snapshot identifier plus items and are accepted only after comparison with live playlist state. [Files reference](https://github.com/crmne/fastpotify/blob/d17b2f0611299d74bcda840ac10be98be1044e62/docs/_reference/settings-and-files.md#where-things-live) [Playlist cache source](https://github.com/crmne/fastpotify/blob/d17b2f0611299d74bcda840ac10be98be1044e62/src/backend.rs#L1494-L1543)
- Spotify remains the remote catalog/library system. Fastpotify's durable local additions are preferences, resumable UI/playback state, local history, credentials, and replaceable caches; the documented storage inventory contains no full catalog or library database. [Stored-data inventory](https://github.com/crmne/fastpotify/blob/d17b2f0611299d74bcda840ac10be98be1044e62/docs/_reference/how-it-connects.md#what-the-client-stores)

## UI and rendering stack

The primary UI uses **egui 0.36**, a pure-Rust immediate-mode GUI, hosted by **eframe 0.36**. Fastpotify disables eframe defaults and selects the **Glow/OpenGL** renderer instead of wgpu, with native Wayland and X11 support; the source calls `eframe::run_native`. There is no HTML/DOM or embedded browser rendering layer. [Dependency manifest](https://github.com/crmne/fastpotify/blob/d17b2f0611299d74bcda840ac10be98be1044e62/Cargo.toml) [Native entry point](https://github.com/crmne/fastpotify/blob/d17b2f0611299d74bcda840ac10be98be1044e62/src/main.rs#L365-L405) [egui project](https://github.com/emilk/egui)

The classic Winamp mini-player is custom-drawn from Winamp 2 `.wsz` skin assets, with its own spectrum analyzer, playlist, and equalizer. The optional MilkDrop window statically links `libprojectM`, which parses MilkDrop presets, analyzes PCM audio, and renders through OpenGL. [Fastpotify README](https://github.com/crmne/fastpotify/blob/d17b2f0611299d74bcda840ac10be98be1044e62/README.md#what-it-does) [projectM architecture](https://github.com/projectM-visualizer/projectm#using-the-library)

## Key dependencies

The manifest identifies these architectural dependencies: `eframe`/`egui`/`egui_extras` for UI; a patched set of librespot 0.8 crates for Spotify sessions, protocol, metadata, playback, and Connect; Tokio for async execution; `reqwest` with rustls for HTTP; `rodio` and `cpal` for the app's guarded local audio sink; `projectm-sys`, winit, and glutin for optional MilkDrop rendering; Serde/JSON for persisted data; `mdns-sd` for receiver discovery; and platform-specific MPRIS/tray/media-control crates. The manifest explains both the Glow-over-wgpu choice and the local librespot/projectM patches. [Cargo manifest](https://github.com/crmne/fastpotify/blob/d17b2f0611299d74bcda840ac10be98be1044e62/Cargo.toml)

## Comparison with Cadence

Cadence is not based on Spotify Soloist. It embeds librespot directly, creates a librespot `Session` and `Player`, and supplies its own CPAL audio sink. Soloist is distributed as a separate headless Linux executable, whereas Cadence is a macOS desktop application. [Cadence playback](../../src/playback.rs) [Cadence audio output](../../src/audio_output.rs) [Soloist overview](https://developer.spotify.com/documentation/soloist/concepts/overview)

Cadence and Fastpotify do share the same broad architecture:

- Both are native Rust Spotify clients without an HTML/browser UI.
- Both separate catalog/library access through Spotify's Web API from local audio playback through embedded librespot, with separate PKCE-based authorization and stored credentials for the two planes. Cadence uses `rspotify` for the Web API; Fastpotify uses its own `reqwest` client and a more elaborate gateway for shared and personal app grants. [Cadence manifest](../../Cargo.toml) [Cadence Web API client](../../src/spotify.rs) [Cadence playback](../../src/playback.rs) [Fastpotify connection model](https://github.com/crmne/fastpotify/blob/d17b2f0611299d74bcda840ac10be98be1044e62/docs/_reference/how-it-connects.md)
- Both isolate Spotify, playback, and async work on a dedicated backend OS thread with a Tokio runtime and communicate with the UI through command/event channels. Both keep playback services alive when the window closes and use single-instance activation. [Cadence backend](../../src/backend.rs) [Cadence services](../../src/app/services.rs) [Cadence lifecycle](../../src/lifecycle.rs) [Fastpotify backend](https://github.com/crmne/fastpotify/blob/d17b2f0611299d74bcda840ac10be98be1044e62/src/backend.rs#L574-L683)

The implementations differ in important ways:

| Area | Cadence | Fastpotify |
| --- | --- | --- |
| UI | GPUI, macOS-focused, GPU-rendered retained entity tree | egui/eframe immediate-mode UI, cross-platform, Glow/OpenGL |
| Web API | `rspotify`, one listener-supplied app registration | Custom `reqwest` client and routing gateway, shared plus optional personal grants |
| Playback control | Direct librespot `Player` commands; no Spirc integration is present | Commands flow through librespot Spirc, making the app a Spotify Connect device |
| Persistence | SQLite for preferences, favorites, queue, history, playback state, and liked-track cache; Keychain for credentials | JSON state/settings/history and disposable file caches; platform state files for credentials |
| Audio | Custom CPAL sink with a ring buffer and resampling | Guarded local sink over rodio/CPAL, plus optional visualization audio path |
| Scope | Minimal macOS player | Cross-platform client with Connect, tray, Winamp mini-player, MilkDrop, lyrics, and broader Spotify operations |

There is no explicit Fastpotify or Soloist attribution in Cadence's current tree or commit messages. Cadence's initial repository baseline on 2026-08-15 already contained GPUI, librespot, rspotify, SQLite, a dedicated Tokio backend, and single-instance lifecycle support. The HN Fastpotify story was posted on 2026-09-01, according to the [HN item API](https://hacker-news.firebaseio.com/v0/item/49517448.json). This proves Cadence's checked-in architecture was not derived from this HN post; it does not prove that Fastpotify itself was never prior art consulted outside the recorded repository history.

## Conclusion

The submission concerns a native, stateful Rust Spotify desktop client, not a new streaming protocol or Spotify backend. Its defining seam is an immediate-mode egui frontend over a channel-isolated async backend, combining Spotify's Web API with embedded librespot playback/Connect and lightweight file persistence. Spotify Soloist, raised by the supplied comment, is an official headless Linux Connect/audio runtime and local integration surface; it is relevant as an alternative receiver engine or companion process, but it is not the Fastpotify project or an equivalent desktop UI architecture.

Cadence is best described as a close architectural peer, not as being based on the linked technology: it independently combines a native Rust UI, Spotify Web API access, embedded librespot playback, a channel-isolated Tokio backend, and durable local state. It is not based on Soloist, and the strongest differences are GPUI instead of egui, direct player control instead of Spirc/Spotify Connect, and SQLite instead of mostly JSON persistence.

For playback, Cadence should retain librespot while monitoring account-level audio-key failures and Soloist's platform and distribution model. Soloist is not a viable migration target for Cadence today.
