# Keychain UX and credential records

Research date: 2026-09-03.

## Decision for Cadence

Keep the Web API token and playback refresh token as separate credentials. Fix release identity first by distributing Cadence with a stable Developer ID signature and notarization. Use one stable local signing identity, or a non-Keychain development store, for repeated development builds. Move from the legacy file-based Keychain to the data protection Keychain after Cadence has the required signing and provisioning setup.

Combining the current values is not the root fix. It would reduce two startup reads to one and therefore halve the visible prompt symptom, but an unstable or untrusted build would still prompt for that record. It would also couple two independently authorized credentials that have separate refresh, invalidation, deletion, and reauthorization lifecycles. Keep them separate unless Cadence deliberately adopts envelope encryption, where one stable Keychain key encrypts a versioned credential document stored elsewhere.

## Apple's model

Apple distinguishes the legacy file-based Keychain from the data protection Keychain. `SecItem` can address either; without `kSecUseDataProtectionKeychain = true` or synchronization, it defaults to the file-based implementation. File-based items use ACLs. Data protection items use Keychain access groups, optionally supplemented by `SecAccessControl`. [Apple TN3137](https://developer.apple.com/documentation/technotes/tn3137-on-mac-keychains)

TN3137 recommends the `SecItem` API and says to default to the data protection Keychain because its behavior is consistent across Apple platforms, it supports newer features, and its access-control model better matches current platform norms. For data protection items on macOS, the process's available access groups come from code-signing entitlements. Those entitlements must be authorized by a provisioning profile embedded in an app-like bundle. [Apple TN3137](https://developer.apple.com/documentation/technotes/tn3137-on-mac-keychains) [Apple access-group documentation](https://developer.apple.com/documentation/security/sharing-access-to-keychain-items-among-a-collection-of-apps)

For file-based items, the creating app is trusted by default. macOS tracks that trust through the app's code-signing designated requirement. A trusted app receives access; an untrusted app triggers the Allow, Deny, or Always Allow dialog. Thus a stable trusted release normally reads any number of its ordinary records silently. Repeated prompts indicate unstable identity, changed ACL trust, or an intentionally interactive access policy. [Apple Code Signing Guide](https://developer.apple.com/library/archive/documentation/Security/Conceptual/CodeSigningGuide/AboutCS/AboutCS.html) [Apple ACL documentation](https://developer.apple.com/documentation/security/access-control-lists)

Stable signing is the Keychain-specific fix. Notarization does not combine records or grant Keychain access; it should accompany Developer ID signing because it is part of a trustworthy macOS distribution path.

The current keyring ecosystem exposes a separate `protected` backend for data protection storage. Its documentation requires code signing with a provisioning profile for all features and describes app-specific access groups. Cadence does not select this backend today. [`apple-native-keyring-store::protected`](https://github.com/open-source-cooperative/apple-native-keyring-store/blob/78cdfff31e8a6579119b75ff7cbfeae7d4fc7d0a/src/protected.rs#L3-L19) [`protected` access groups](https://github.com/open-source-cooperative/apple-native-keyring-store/blob/78cdfff31e8a6579119b75ff7cbfeae7d4fc7d0a/src/protected.rs#L21-L56)

## Conclusion

Separate records are common and are not inherently bad Keychain UX. Zed, GitButler, GitHub Desktop, and Sequel Ace all maintain multiple logical credentials as separate records. Stable trusted builds normally read ordinary records silently. Repeated prompts are the bug or symptom to fix.

Priorities for Cadence:

1. **Developer ID signing and notarization:** make the release bundle identifier and designated requirement stable across versions. Replace the current ad-hoc release default and add notarization before changing credential shape.
2. **Stable development identity:** use `run-signed.sh` with the same local identity across rebuilds, or follow Zed and GitButler with a development-only non-Keychain credential store. Do not train developers or users to accept recurring prompts.
3. **Data protection migration:** once Cadence has an Apple team, provisioning profile, and signed app bundle, move to `SecItem` targeting the data protection Keychain and a private access group. Plan migration of the two existing login-Keychain records rather than silently abandoning them.
4. **Retain independent credentials:** keep `oauth-token` and `playback-refresh-token` separate because Spotify authorizes and revokes them independently. Merge only as part of an intentional envelope-encryption design with one Keychain-held encryption key, authenticated ciphertext, versioning, atomic updates, and explicit per-credential deletion semantics.

Merging just the two current values would hide half of an unstable-signature symptom while weakening independent lifecycle and revocation. It is not the root fix.
